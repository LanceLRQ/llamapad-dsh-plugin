## P0-1 思考强度：插件的「不支持」前提已被推翻

**插件现状**

- `src/adapter.ts:58` 注释：「reasoning 刻意省略：llama.cpp 无 reasoning-effort 控制（契约：省略 = 无此能力）」
- `src/adapter.ts:63-65`：`stream()` 里 `options.reasoningEffort !== undefined` 时无条件
  `throw new LlmError(..., "UNSUPPORTED")`

**面板变更**（llamapad `cd8c028` / `a9dffee` / `853fff6`，2026-09-01 那批）

1. 模型级 `server.reasoning_effort` 配置（`core/schemas.ts:144`，`"inherit"` 为「跟随模板默认」哨兵值），
   `enable_thinking` 同批改走 CLI 参数而非环境变量
2. 新增 `api` 段配置：`api.effort_aliases`（显式别名表）+ `api.effort_rounding`（`down`/`up`/`off`，
   `core/schemas.ts:157-158`）
3. **中转层会替调用方改写**：`lib/proxy-rewrite.ts` 的 `rewriteRequestBody` 在
   `/v1/chat/completions`、`/chat/completions`、`/apply-template` 三条路径上，按当前运行模型的
   chat template 值域做「别名映射 → 值域内透传 → 就近取整 → 丢弃字段」四级决议。
   兜底策略贯穿全部分支：**改写不了就删掉字段让模板走自身默认，保证请求一定不失败**
   （`lib/effort-mapping.ts` 的 `resolveEffort`，判定顺序即规格）
4. `GET /api/v1/proxy/llama/v1/models`（及别名 `/models`）的响应被增强：每个 `data[]` 条目补
   `supported_parameters: ["reasoning_effort"]` 与
   `x_llamapad.reasoning_effort.{supported, levels, aliases, rounding}`（`lib/proxy-rewrite.ts`
   的 `enhanceModelsResponse`）
5. 发生改写时响应头带 `x-llamapad-reasoning-effort`，形如 `max->xhigh (alias)` /
   `banana->dropped (unsupported)`；请求体超 4MB 或 `content-length` 缺失时跳过改写，
   头置 `skipped (body too large)`

**为什么这是真缺陷**：面板已经把「客户端发什么都能正常工作」这件事做完了，插件却在入口把用户的
选择直接打回。用户在 dsh 里选了思考强度就报错，而同一台面板上 Cherry Studio 一类客户端却工作正常。

**dsh 侧契约**（`node_modules/@deepseek-ai/dsh-llm/lib/types/types.d.ts:231-257`、`brand.d.ts:44`）

```ts
type ReasoningEffortId = Branded<'ReasoningEffortId'>;   // opaque string，无枚举约束
interface LlmReasoningEffortInfo { id: ReasoningEffortId; name: string; description?: string }
interface LlmModelReasoningInfo { efforts: readonly LlmReasoningEffortInfo[]; defaultEffort?: ReasoningEffortId }
interface LlmResolvedModelInfo extends LlmModelInfo { context?: ...; reasoning?: LlmModelReasoningInfo }
```

档位由 adapter 自己定义，面板的 `levels`（如 `["xhigh","medium","low"]`）可直接映射，两边对得上。

**应做**

- **proxy 模式**：不再拒绝，把 `reasoningEffort` 原样放进请求体交给中转层改写
- **resolveModel**：上报 `reasoning: { efforts }`，档位取自 `x_llamapad.reasoning_effort.levels`
- **direct 模式**：绕过中转 → 没有改写保护，值域外的值会被 jinja `raise_exception` 打成 HTTP 500
  （`lib/reasoning-effort.ts` 文件头有实测记录：容器照常启动、`/health` 照常 200，只在真正推理时炸）。
  这里必须保留拒绝，或自行按 levels 校验
- 可读 `x-llamapad-reasoning-effort` 头做诊断

**已知约束（实现时必须处理）**：中转层增强 `/v1/models` 时用的是 `info.model`，即**当前运行中的那个
模型**。因此非运行中模型拿不到自己的 `levels`——`resolveModel` 对未运行模型只能省略 `reasoning`
或退回完整枚举，不能假装知道。

## P0-2 `start` / `stop` 的 409 被误报成「面板不可达」

llamapad `fb36792` 给启停加了互斥（`RuntimeBusyError`），并发的第二个请求返回 **409**
（`api/v1/models/[name]/start/route.ts` 与 `stop/route.ts` 同款处理）。

插件 `src/panel-client.ts:170-193` 的 `startModel` / `stopModel` 只判 404 / 422 / 401，
409 落进 `PANEL_HTTP`，再被 `src/switching.ts` 的 `ensureOnce` 统一映射成 `PANEL_UNREACHABLE`。

**后果**：A 形态 auto-switch 档、B 形态 `llamapad_start_model` 工具、设置卡片启停按钮三者撞车时，
用户看到「llamapad 面板不可达」——面板好好的，只是上一个启停请求还没结束。文案把一个可重试的
瞬态冲突说成了网络故障。

**应做**：新增 `RUNTIME_BUSY` 错误码 + 中文文案，`EnsureErrorCode` 同步扩充，
`adapter.ts:mapEnsureError` 的白名单一并放行。是否自动短暂重试留待方案决定。

## P0-3 422 现在有两种成因

`a9dffee` 之后 `start` 的 422 既可能是模型文件缺失，也可能是 `ReasoningEffortNotAllowedError`
（`reasoning_effort` 取值不被该模型 chat template 接受，启动前拦下）。面板 route 注释与
`docs/guide/zh/api.md:60` 都明确写了这两种。

插件 `src/panel-client.ts:175` 一律映射成 `MODEL_FILES_MISSING`，第二种情况会给出一句完全不相干的
「模型文件缺失」。

**应做**：按响应体 message 区分，或把 code 改成中性的 `START_REJECTED` 并把面板的 message 透传给
用户（面板的错误 message 是中文且自解释，这是 runtime 层的既定错误契约）。

## P1-4 `runtime/status` 新增 `ready`，插件完全没用上

llamapad `12cfd84` 起 `RunningModelView` 有 `ready: boolean`（llama-server 是否已开始监听），
面板侧 `server/readiness.ts` 带 2s 缓存且缓存的是 promise（防惊群），探测超时 1.5s。

三处可受益：

1. **`src/routing.ts` 的判定有漏洞**：strict / passthrough 只看 `status.running` 非空就判 `proceed`。
   但**容器起了、llama-server 还没监听的窗口真机实测有 35 秒**（`readiness.ts` 头注释：27B 模型容器
   启动 10s、`listening` 出现在 34s 之后）。这期间 chat 打过去被中转层回 502「容器端口未就绪」，
   插件抛 `PROVIDER_HTTP_ERROR`，文案对用户毫无指导。读 `ready` 就能给出「模型正在加载」的准确提示
2. **`src/switching.ts` 的就绪轮询**可以直接读 `status.ready`，省掉每轮独立的 `llamaHealth()` 往返
3. **`src/panel-gateway.ts:134`** `resolvePhase` 里那次额外的 `llamaHealth()` 同样可省

**应做**：`PanelRuntimeStatus.running` 类型补 `ready`，顺带补 `container` / `configStale`
（面板一直在返回，插件类型没声明）。routing 的判定改动涉及行为语义，需在方案里单独决策。

## P1-5 `ModelView` 新增字段

面板 `server/modelsView.ts` 的 `ModelView` 现在还有 `configStale`（模型运行中且启动后配置又被保存过
——运行容器参数不会热更新）、`createdAt`、`fileCount`、`ggufFile`、`mmprojFile`。

`configStale` 对 `adapter.ts:describeModel` 有价值：可在选择器里标一句「配置已变，重启生效」，
与现有的 `●` 运行中前缀、缺件提示是同一类信息。

## P2-6 短地址别名 `/llama-proxy/*`

llamapad `981c3f8` 经 Next rewrite 新增，不动任何 handler，转发出去的上游 URL 与长地址一字不差
（中转 handler 拼上游地址时只用 catch-all 的 `params.path` 与 query，请求前缀不参与）。

插件不必改代码。README / 文档里提一句等价写法即可。

## P2-7 CLAUDE.md 待办「关注 llamapad M5」可结案

**但这条待办不能简单打勾**：真正需要跟进的是同一路由上新长出来的改写层（见 P0-1）。措辞要改写。

| `/api/v1/models/:name/effective` 的 `merged` | 仍是 `mergeConfig(defaults, overrides)`，新增的 `api` 段是增量，不影响 `readCtxSize` |

## 顺带发现（面板侧，超出本插件范围）

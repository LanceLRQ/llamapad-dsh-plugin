# dsh 0.2.0 → 0.2.1 插件对接面差异调研（2026-10-17）

> 结论先行：**0.2.1-rc.1 对本插件的全部对接面都是加法变更或等价重构，插件源码零改动即可
> 兼容**。唯一的硬阻断仍是插件管理器按 peerDependencies 范围做的兼容门禁，旧范围
> `<0.2.1-0` 在 0.2.1 宿主上会被拒装；把三个 `@deepseek-ai/dsh-*` peer 的上限扩到
> `<0.2.2-0` 即解决。
>
> 方法：npm 拉 `0.2.1-rc.1` 全部相关框架包，与本仓库 devDependencies（0.2.0-rc.2）逐包
> diff `lib/`（类型 + 运行时），重点核对派发路径对 adapter 的调用面与 strict codec 的
> 消费入口。另抽查 `0.2.1-rc.2`（npm `next` tag）：五个关键包 rc.1→rc.2 的 `lib/`
> **零差异**，peer 范围覆盖整条 0.2.1 线（rc.x + 正式版）是安全的。

## 插件管理器的兼容门禁（本轮唯一要改的东西）

`@deepseek-ai/dsh-app-boot@0.2.1-rc.1` 的 `evaluatePluginCompatibility`：

- 仍是 `semver.satisfies(runtimeVersion, range, { includePrerelease: true })`；
- **新增语义**：插件可在 package.json 声明 `engines.dsh` 范围，声明后它单独裁决、
  peerDependencies 被忽略；不声明则照旧只检查 `@deepseek-ai/dsh` 与 `@deepseek-ai/dsh-*`
  开头的 peer。本插件不声明 `engines.dsh`，走原 peer 校验路径，扩上限即放行
  `0.2.1-rc.x` 与 `0.2.1`。

## 版本与发布事实

- npm：`@deepseek-ai/dsh` dist-tags `latest` = `0.2.0-rc.2`、`next` = `0.2.1-rc.2`；全部
  `dsh-*` 框架包同步发了 `0.2.1-rc.1`/`0.2.1-rc.2`。
- 0.2.1 代宿主的 cordis/schemastery 钉 `~4.0.5` / `~3.18.5`（如上，零功能差异）。

## 采纳的改动

1. peer 三项 `>=0.1.5-rc.3 <0.2.1-0` → `>=0.1.5-rc.3 <0.2.2-0`（上限收到 0.2.1 一代，
   0.2.2 出来后按惯例先跑矩阵再扩）。
2. devDependencies 的 `@deepseek-ai/dsh-*` 全部 0.2.0-rc.2 → 0.2.1-rc.1、cordis
   4.0.4 → 4.0.5、schemastery 3.18.4 → 3.18.5（类型检查基线换到最新一代，对齐宿主代）；
   `typecheck` 零错误，佐证「全是加法」。
3. `scripts/test-compat.mjs` 矩阵从两代扩成三代：0.2.0-rc.2（cordis 4.0.4 /
   schemastery 3.18.4）+ 0.1.7-rc.1（4.0.4 / 3.18.4）+ 0.1.5-rc.3（4.0.2 / 3.18.2）。
